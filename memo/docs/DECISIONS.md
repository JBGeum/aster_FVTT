# Aster FVTT — 설계 결정 일지 (Decision Log)

> 개발 중 내린 주요 설계 결정과 그 이유를 기록. 각 항목: **결정 / 배경 / 대안 / 선택 이유**.
> 목적: (1) 나중에 "왜 이렇게 했지?"를 되짚기, (2) 협업·인수인계, (3) 포트폴리오(설계 사고의 증거).
> 형식은 ADR(Architecture Decision Record)을 가볍게 변형.

---

## D1. 인벤토리: 참조 방식 vs 중첩 저장

**결정:** 아이템이 `container` 필드(가방 id, ""=창고)로 소속을 가리키는 **참조 방식**. 가방 안에 아이템 데이터를 물리적으로 품지 않음.

**배경:** 그리드 인벤토리에서 아이템이 어느 가방에 들어있는지를 표현해야 함.

**대안:** 가방 아이템의 데이터 안에 소속 아이템들을 배열로 임베드(중첩 저장).

**선택 이유:** 관계형 DB의 외래키 정규화와 같은 논리. 중첩 저장은 아이템 이동 시 양쪽 데이터를 동기화해야 하고 중복·불일치 위험이 큼. 참조 방식은 아이템의 `container`만 바꾸면 이동이 끝나 단순하고 일관적. Foundry의 아이템은 액터에 평면적으로 저장되므로 참조가 구조에도 맞음.

> 백엔드 관점: NoSQL의 embedding vs referencing 논쟁과 동형. "함께 자주 바뀌고 항상 같이 읽히면 embed, 독립적이면 reference"에서 인벤토리 아이템은 독립적이라 reference.

## D2. 인벤토리 배치: 클릭-선택 vs 드래그앤드롭

**결정:** 칸을 클릭해 선택 후 배치하는 **클릭-선택 방식**. 드래그 아님. 겹침 허용, 회전 없음.

**배경:** 그리드에 아이템을 놓는 인터랙션 방식 선택.

**대안:** 드래그앤드롭(직관적이나 구현·터치 대응 복잡).

**선택 이유:** 드래그는 좌표 계산·프리뷰·터치 이벤트·재렌더 충돌 등 구현 복잡도가 높음. 클릭-선택은 단순하고 버그 표면이 작으며, Foundry 시트 재렌더와 충돌이 적음. 게임플레이상 정밀 배치가 필수도 아니라 비용 대비 효용에서 클릭-선택이 우위.

## D3. 공방(craft): 자원 차감 vs 비용 합계 비교 ~~[현행]~~ [D14로 갱신됨]

**결정:** 스킬 취득 시 자원을 **차감하지 않음**. 대신 "취득한 스킬들의 비용 합 ≤ 보유 자원"을 항상 비교만. 초과 시 취득 거부 + 이미 초과면 빨강 표시.

**배경:** 공방 스킬에 마테리얼/아스테르 비용이 있음.

**대안:** 취득 시 자원을 실제로 차감(소비).

**선택 이유:** 자원은 시나리오·정동판정으로 별도 증감되고, 스킬은 "보유 자원 한도 내에서 유지되는 상태". 차감 방식이면 자원이 줄었을 때 이미 취득한 스킬을 어떻게 처리할지 모호해짐(강제 해제?). 합계 비교 방식은 "현재 보유로 이 스킬들을 감당 가능한가"를 그때그때 보여줘 규칙과 자연스럽게 맞고, 취득 시점 거부와 상시 초과 표시를 **같은 함수로** 처리(중복 제거).

## D4. spell·record: 아이템 타입으로 저장

**결정:** 마법(spell)과 세션 기록(record)을 각각 **아이템 타입**으로 저장(액터 소유 아이템).

**배경:** 여러 개가 추가/삭제·개별 편집되는 데이터.

**대안:** 액터 system 안에 배열로 직접 저장.

**선택 이유:** 추가/삭제·개별 시트·드래그가 필요한데, 이는 Foundry 아이템 시스템이 기본 제공. 배열 직접 관리는 추가/삭제/편집 UI를 전부 손으로 만들어야 하고 폼 바인딩도 까다로움. "아이템 = 물건"이 아니라 "캐릭터에 속한 데이터 묶음"으로 보면 마법·기록도 자연스럽게 아이템. (spell이 아이템인 패턴을 record에 재사용.)

## D5. 특기색: 신규 필드 vs 기존 `system.color` 재활용

**결정:** 액터의 기존 `system.color` 필드를 특기색으로 재활용. 신규 필드 추가 안 함.

**배경:** 마법판정에서 "특기색 일치 시 +1" 규칙 필요.

**대안:** `system.specialty` 같은 새 필드 신설.

**선택 이유:** 이미 시트 헤더에 색 선택 드롭다운(`system.color`)이 존재하고 의미가 정확히 일치. 새 필드는 중복. 기존 필드 재활용이 스키마를 단순하게 유지.

---

## D6. 인라인 문법: Foundry 표준 vs 자체 파서

**결정:** 마법 effect 텍스트의 변수·다이스는 **Foundry 표준 문법만**(`[[/r ...]]`, `@ability.knowledge.total`). 자체 파서 안 만듦.

**배경:** effect에 "사용자의 박식만큼 감소" 같은 동적 값 표현 필요.

**대안:** `{박식}` 같은 자체 토큰을 만들고 출력 시 치환하는 파서 구현.

**선택 이유:** Foundry의 `enrichHTML` + `getRollData()`가 표준 문법을 이미 자동 처리. 자체 파서는 토큰 사양 정의·치환 로직·유지보수 비용이 추가됨. "처음엔 표준으로, 정말 불편하면 그때 자체 문법"이라는 점진 원칙. 현재는 표준으로 충분.

---

## D7. 경계도(alert): world 값으로 분리

**결정:** 경계도를 파티 공유 **world setting**(`alertLevel`, `world-values.mjs`)으로 저장하고 GM 패널에서 관리. 캐릭터 값과 엄격히 분리.

**배경:** 경계도는 특정 캐릭터가 아니라 파티 전체가 공유하는 값.

**대안:** 액터 system에 두거나, 액터 시트에 편집 UI.

**선택 이유:** 캐릭터 소유 값이 아니므로 액터에 두면 "누구의 시트에서 바꾸지?"가 모호하고 여러 시트에 중복 표시됨. world setting이 공유 값의 올바른 저장소. 편집은 GM 전용 패널로(소유 주체에 UI를 맞춤). spell 카드는 경계도를 표시만 하고 실제 변경은 패널/버튼으로 — 의존성 분리.

---

## D8. GM 패널: 확장 가능한 값 정의 패턴

**결정:** world 값을 `WORLD_VALUES` 배열에 정의하고 패널이 그걸 읽어 UI를 자동 생성. 새 값은 배열에 한 줄 추가.

**배경:** 지금은 경계도 하나지만 향후 world 값(세션 페이즈 등)이 늘 수 있음.

**대안:** 경계도 전용 UI를 하드코딩.

**선택 이유:** 하드코딩은 값이 늘 때마다 UI를 새로 만들어야 함. 정의-주도(definition-driven) 패턴은 배열 한 줄 + setting 등록만으로 확장. 지금 없는 값을 억지로 만들지 않으면서 확장은 쉽게.

---

## D9. record 카드: 책 넘기기 vs 가로 스크롤

**결정:** 세션 기록 카드를 한 번에 한 장씩 **책 넘기기**(◀▶ + n/전체)로 표시. 가로 스크롤 아님.

**배경:** 기록 카드가 여러 개. 카드마다 필드가 많음(도시·경계도·펠카·우호도·시나리오수·체재지모습·관련인물·긴 메모).

**대안:** 카드를 작게 만들어 가로로 스크롤 나열.

**선택 이유:** 정보량이 많은 카드를 작게 줄이면 비좁아 메모도 못 읽고 입력도 힘듦. 한 장씩 크게 = 모든 필드가 시원하고 메모도 넉넉. "정보 많은 카드엔 페이지네이션"이 맞음. 메모 길어지면 카드 내부 세로 스크롤로 카드 높이 일정.

## D10. 레이아웃: 우측 px 고정 + 좌측 흡수 + 컨테이너 쿼리

**결정:** 좌(캐릭터)/우(인벤토리) 분할에서 **우측을 px 고정**, 좌측이 나머지 폭 흡수. 아스테르 6칸은 컨테이너 쿼리로 6×1↔3×2 통제된 2단계.

**배경:** 시트 resize 시 인벤토리 격자가 과대/과소해지는 문제, 좌우 높이 불균형.

**대안:** 좌우를 비율(fr)로 분할, 아스테르를 auto-fit으로 완전 자동 배열.

**선택 이유:** 인벤토리 격자는 적정 너비가 정해져 있어 비율로 늘리면 칸이 과대해짐 → 우측 px 고정이 맞음(늘어난 폭은 좌측이 흡수). 아스테르는 6개(3으로 깔끔히 나뉨)라 auto-fit의 "5+1" 같은 어중간한 배열이 보기 싫음 → 6×1↔3×2 통제된 2단계가 예측 가능하고 깔끔. 화면이 아닌 부모 너비 기준이라 `@media`가 아닌 `@container` 사용(Foundry 시트는 창 resize라 화면 기준이 부정확).

---

## D11. 순수 함수 분리 (테스트 용이성)

**결정:** 비용 검사·판정 계산·용량 검사 등 로직을 Foundry API에 의존하지 않는 **순수 함수**로 `helpers/`에 분리.

**배경:** 게임 로직이 시트·문서 코드에 섞이면 테스트·재사용이 어려움.

**대안:** 시트/액터 메서드 안에 로직을 직접 작성.

**선택 이유:** 순수 함수는 Foundry 없이 Vitest로 검증 가능(브라우저 불필요, 빠름, 회귀 방지). Java에서 비즈니스 로직을 프레임워크(Spring)에서 서비스 계층으로 분리하던 것과 같은 원리. 관심사 분리로 "로직 오류"와 "UI/런타임 오류"를 분리해 디버깅이 쉬워짐. 면접에서 지적받은 "엔지니어링 깊이"를 직접 채우는 설계.

## D12. 자동화의 경계: 처리만 보조, 룰은 안 바꿈

**결정:** 판정 후속(아스테르 획득·경계도 상승 등)을 자동화하되, 색 선택·개수·양도·적용은 **버튼으로 사람이 확정**. 완전 자동 지급 안 함.

**배경:** 공식 룰의 자동 후속(판정 후 자동 후속 효과)을 Foundry로 편하게.

**대안:** 굴림 성공 시 시스템이 자동으로 아스테르 지급·경계도 가산.

**선택 이유:** 룰상 색·개수는 GM 지정, 아스테르는 양도 가능 등 **사람 판단이 개입**하는 지점이 있음. 완전 자동은 GM 재량을 침해하고 양도 같은 케이스를 못 다룸. "GM이 손으로 하던 계산을 버튼으로 대체"까지가 자동화의 올바른 선. 룰 자체는 바꾸지 않음.

---

## D13. 마이그레이션/정정: 점진적, 코드 우선

**결정:** V13 마이그레이션·정정을 위험도 순 단계별 커밋으로. 명세 문서와 실제 코드가 충돌하면 **코드 우선**.

**배경:** ApplicationV2 전환, deprecated API 정리 등 breaking change 다수.

**대안:** 한 번에 전면 전환.

**선택 이유:** 한 번에 바꾸면 어디서 깨졌는지 추적이 어려움. 단계별 커밋은 문제 발생 시 범위를 좁힘(실무의 점진 마이그레이션). 명세는 골격·패턴이고 실제 구현이 진실이므로, 둘이 어긋나면 코드를 따름(예: size가 명세엔 배열이나 코드는 객체 → 코드가 정답).

## D14. 공방(craft): 자동 차감 + 환불 정책으로 전환 (D3 갱신)

**결정:** 노드 체크 시 **자동 차감**(음수 허용 + 경고), 언체크/리셋 시 **자동 환불**. `anyAster`(임의색)는 자동 처리 대상에서 제외하고 시트 입력란으로 수동 조정.

**배경:** D3는 자원을 차감하지 않고 합계 비교만 하는 정책이었으나, (1) 공식 룰의 자원 소비 표현은 소비 뉘앙스에 더 가깝고, (2) 시트의 자원 값이 "총 보유"인지 "사용 가능 잔여"인지 모호해져 멘탈 모델 부담이 있었다.

**대안:**
- D3 유지 (합계 비교만)
- 자동 차감 + 환불 없음 (룰적으로 확정 후 환불 불가에 충실)
- 수동 차감 (체크는 상태, 별도 확정 버튼)

**선택 이유:** 자동 차감으로 공식 룰의 자원 소비 표현에 충실하면서, 환불은 사용자의 체크 해제 행동을 "임시였음"의 신호로 신뢰해 허용. 룰적 확정 후 환불 불가의 "확정" 경계를 시스템 외부(사용자 의도)에 둠. 수동 차감(별도 확정 버튼)은 미확정 상태라는 새 개념이 필요해 UI·상태 관리 비용이 큼.

음수 허용은 차단보다 알림으로 수정 유도가 GM 재량을 침해하지 않는다(D12 자동화 경계 원칙). `anyAster` 제외는 룰 표현 "임의의 아스테르 1종" 자체가 PL 판단을 요구하므로 자동화 부적합.

> **D3 → D14 변경 의미:** 결정 일지의 일관성을 위해 D3는 보존하고 supersession만 표시. "왜 D3가 그렇게 결정됐고, 왜 갱신됐는가"의 흐름이 결정 사고의 증거가 된다.

## D15. 파생 스탯(민첩·회피): 순수 파생, 시트는 표시 전용

**결정:** `system.speed`(민첩)와 `system.dodge`(회피)를 `prepareDerivedData`에서 능력치로부터 자동 계산. 시트는 표시 전용(`<span>`)으로 두어 직접 편집 불가.

**배경:** 공식 룰에 명확한 계산식이 있음(능력치 조합으로 결정되는 파생 값). 이전 코드는 식이 서로 뒤바뀌어 있었고, 시트는 input으로 직접 편집을 시도해 prepareDerivedData와 충돌하는 상태였다.

**대안:**
- ability와 동일한 `{total, base, mod}` 패턴 — `base`를 룰 식으로 자동, `mod`로 상황 보정 입력 가능
- 입력란 유지 + 자동 계산 제거 — 사용자가 매번 계산

**선택 이유:** 상황 보정(상태이상·액션 보정 등)은 Active Effect(D16)에서 `system.speed`에 가산하는 방식으로 별도 처리하므로, 이 단계는 base 계산에만 집중. `mod` 필드를 두면 Active Effect와 역할이 겹쳐 어느 쪽이 진실인지 모호해진다. 입력란 유지는 입력 실수·갱신 누락의 원인이 되므로 부적합.

> Foundry DataModel의 `prepareDerivedData` 표준 패턴을 정확히 따르는 첫 사례. Active Effect 도입(D16)이 이 derived 값에 자연스럽게 얹힌다.

## D16. 상태이상 Active Effect 단방향 동기화 (피로·졸림 우선)

**결정:** 시트 badstatus 체크박스를 진실로 두고, 변경 시 시스템이 표준 Active Effect를 자동 생성/삭제하는 **단방향 동기화**. 사용자는 AE를 직접 조작하지 않음. 첫 적용 대상은 피로·졸림.

**배경:** 공식 룰 상태이상은 수치 영향(상태이상별 수치 영향)이 명확. 체크박스만으로는 효과가 실제 스탯·판정에 반영되지 않아 GM 수동 계산 부담.

**대안:**
- AE를 단일 진실로 (badstatus boolean 제거, AE 존재 여부로 판단)
- 양방향 동기 (badstatus ↔ AE 둘 다 변경 가능)
- 체크박스 없이 AE 탭만 사용

**선택 이유:** 양방향은 동기 루프·race condition 위험. AE 단일 진실은 template.json·DataModel 정리 비용이 크고 기존 UI 변화. 단방향은 UI 변화 0, 메커니즘 단순, race 위험 최소.

이번 범위(피로·졸림)는 자동화 효과가 명확한 두 가지로 시작. 부상/큰부상은 트리거 정의가 모호(전투/이동 시점)해 별도 검토. 배고픔은 포만 자동 감소 도입 후 연동.

피로의 수치 영향은 AE `changes`로 `system.speed`에 직접 가산. 졸림은 임시 보정 값라 AE로 표현 어려워 `rollAbility`에서 직접 보정. 룰의 "1회 판정 실패 시 졸림 해제"는 일반판정 실패 시 자동 해제(대결판정·정동판정·마법판정은 실패 정의가 모호하거나 룰상 보정 자체가 없어 범위 밖).

> Foundry V13의 Active Effect changes 메커니즘 첫 적용 사례. `system.speed`가 derived(D15)이므로 AE가 그 위에 가산되어 최종값을 형성하는 표준 패턴 검증.

## D17. 세션 페이즈 트래커 — WORLD_VALUES 확장으로 도입

**배경:** 룰적으로 페이즈마다 규칙이 다름(특히 탐색 페이즈의 포만 감소). 시스템이 "현재 페이즈"를 알면 후속 자동화(포만 보정 등)가 정확해진다.

**대안:**
- 별도 페이즈 전용 UI/모듈 신설
- 페이즈를 액터별 값으로 관리
- 자동 이행 (이벤트 트리거로 페이즈 자동 변경)

**선택 이유:** GM 패널의 `WORLD_VALUES` 패턴이 이미 definition-driven으로 만들어져 있음. 새 type 분기 하나 + 정의 한 줄로 확장. 별도 모듈은 과잉. 페이즈는 파티 공유 값이므로 액터별 관리 부적합(D7과 같은 논리). 자동 이행은 룰상 GM이 흐름 주관 → 자동화하면 GM 재량 침해(D12).

**확장성 검증 — WORLD_VALUES 패턴(D8)의 회수:** definition-driven 설계가 두 번째 값 추가에서 비용 거의 0임을 확인. 향후 동일 패턴으로 추가 가능.

> 구현 메모: V13 ApplicationV2의 `data-action`은 click 전용이라 `<select>`의 change는 `_onRender`에서 수동 등록(addEventListener). 패널 동기화는 기존 `updateSetting` hook이 `WORLD_VALUES` 기반이라 자동 처리.

## D18. 판정 보정 통합 — `penalties` 객체로 일원화

**결정:** 졸림·포만 등 판정 달성치 보정을 `penalties = { sleepy, satiety, total }` 객체로 통합. `computePenalties(actor)` 순수 함수가 액터 상태에서 보정을 계산. `computeSpellRoll`의 `statusPenalty: number` 인자도 `penalties` 객체로 시그니처 변경.

**배경:** E1에서 졸림 보정만 `statusPenalty`로 도입했으나, 포만 보정 추가로 인자가 추가될 때 시그니처가 자꾸 늘어나는 문제. 카드에서도 어느 보정에서 얼마가 왔는지 분리 표시가 어려움.

**대안:**

- 보정을 모두 합쳐 단일 숫자(`statusPenalty: number`)로 유지
- 보정마다 별도 인자 (`statusPenalty`, `satietyPenalty`, ...)
- 보정을 객체 배열 (`penalties: [{key, value}, ...]`)

**선택 이유:** 객체(`{ sleepy, satiety, total }`)는 (1) 항목별 카드 표시 자연, (2) total 사전 계산으로 호출자 편의, (3) 향후 보정 종류 추가가 키 한 줄 추가로 끝남(시그니처 변경 없음). 배열은 키 비교가 번거롭고, 단일 숫자는 분리 표시 불가, 별도 인자는 확장 시마다 시그니처 변경.

`computePenalties`는 순수 함수로 분리 — 액터 상태(졸림 boolean, 포만 number)만 보고 결정하므로 mock으로 Vitest 가능. D11(관심사 분리·테스트 용이성) 회수.

> **룰 정합 — 페이즈와 보정의 분리:** 보정 자체는 페이즈 무관. 페이즈 의존은 포만 _감소_에만 있음. v1 명세에서 이 둘을 묶어 추측했던 오류를 룰 재독으로 정정.

## D19. 장면 이동 — GM 패널의 공용 트리거 메커니즘

**결정:** 공식 룰의 장면 전환(이동 = 룰적 장면 전환, 토큰 이동 아님)을 GM 패널의 **명시적 액션 버튼**으로 도입. 다이얼로그에서 대상 PC를 GM이 직접 선택(기본 전체). 탐색 페이즈일 때만 선택된 PC의 포만이 자동 감소(특정 상태일 때 가중).

**배경:** 공식 룰은 탐색 페이즈 진행 시 자원 감소이고, 같은 장면 전환 트리거 위에 피크닉(공식 룰, 이동 전 타이밍)과 부상 자동 적용(공식 룰, 탐색 페이즈 이동 시 체력 차감)도 얹혀 있다. 즉 장면 이동은 세 메커니즘의 공용 진입점.

처음에는 장면 전환을 Foundry의 토큰 이동 hook으로 자동 감지할까 검토했으나, 사용자 정정으로 룰적 장면 전환은 *장면 단위 진행*(예: 도시→던전)임이 확인됨. 토큰 hook은 false positive(GM의 위치 미세 조정 등) 위험이 컸음.

**대안:**
- Token movement hook 자동 감지 (false positive 위험)
- 시트별 "장면 전환 완료" 버튼 (모든 PC가 각자 누름 — 마찰 큼)
- 자동화 안 함 (시트 input 직접 편집)

**선택 이유:** GM 패널의 명시적 액션은 (1) false positive 0, (2) 한 번 클릭으로 다수 PC 일괄 처리, (3) 파티 분산 시나리오에서 대상 선택 가능, (4) 향후 피크닉·부상 트리거를 같은 흐름에 얹을 수 있는 공용 기반. D12(사람이 버튼으로 확정) 원칙과 일치.

페이즈와 효과의 분리: 장면 이동 자체는 모든 페이즈에서 일어날 수 있는 개념적 이벤트(예: 정보수집 페이즈에서도 도시 안 장소 이동 가능). 룰상 *포만 감소*만 탐색 페이즈 한정이므로, 버튼은 항상 노출하고 효과만 페이즈별로 분기. 향후 부상/피크닉이 페이즈별로 다른 효과를 가질 때도 같은 패턴 재사용.

> 메커니즘 재사용 — D20(피크닉)도 동일 "장면 이동/이동 전" 트리거 위에 얹힐 수 있었으나, F1 구현 시점에 PL 주도(시트의 요리 버튼) 흐름이 룰적으로 더 자연스럽다고 판단해 별도 진입점으로 결정. 두 흐름은 공존 가능.

## D20. 피크닉 회복 — food 모델 확장 + PL 즉시 회복

**결정:** food 아이템에 `restore: number`(양도 가능 회복량) + `bonusEffect: string`(양도 불가 추가효과) 필드 추가. PL이 시트의 요리 아이템에서 "피크닉" 버튼을 누르면 **GM 수락 단계 없이 본인 포만이 즉시 회복**되고, PL(요리한 PC) 화자로 결과 카드가 출력됨.

**배경:** 공식 룰의 피크닉 메커니즘 자동화. 회복량은 양도 가능, 추가효과는 양도 불가라는 룰의 비대칭을 데이터 모델에 명확히 반영.

**대안:**

- 단일 `restore` 필드만 (추가효과는 `effect` 필드에 텍스트로 섞음)
- GM 패널에 피크닉 액션 (PL 선언 흐름 자동화 안 함)
- **GM이 채팅 카드의 "수락" 버튼으로 확정하는 2단계 흐름** (F1 최초 구현안)
- 양도까지 한 STEP에 (F2와 묶음)

**선택 이유:** 단일 필드는 룰의 양도 가능/불가 구분을 표현 못함 → 양도 STEP(F2) 도입 시 데이터 마이그레이션 필요. GM 패널 액션은 룰의 "PL 선언 → GM 판단"을 시스템적으로 거꾸로 만듦. F1·F2 분할은 (1) F1만으로도 룰의 기본 동작(피크닉 + 본인 회복) 완결, (2) 양도는 PL 간 수동 가능, (3) F1·F2 명세를 한 번에 검증하기보다 단계적이 안전.

> **정정 — GM 수락 2단계 제거(사용자 결정):** 최초 구현은 "PL 선언 카드 → GM 수락 버튼 → 회복"의 2단계였으나, GM 수락 과정 없이 PL이 누르면 바로 자동 회복되도록 단순화. 공식 룰의 GM 판단 부분은 GM이 탐색 페이즈를 유지/전환하는 것으로 충분히 게이팅된다고 보고, 운영 마찰(GM 클릭 대기)을 제거. 부수 효과로 중복 수락 방지 flag·`picnic-accept` 훅·선언/결과 2개 카드가 모두 불필요해져 코드가 단순해짐(선언과 결과를 단일 카드로 통합, 화자는 요리한 PC). 회복은 `satiety.value`의 `min:0`/`max` 클램프가 보장.

> 시나리오 2회 제한은 시스템 미강제 — 공식 룰의 특별한 지시 없는 경우라는 단서를 GM 재량으로 해석. 카운터 도입 시 record 시트의 시나리오 단위 데이터와 묶어 검토 가능(별도 STEP).

> **구현 메모 — `effect` 중복 제거:** base item 템플릿에 이미 `effect`가 있어 food의 `effect: ""`(template.json)는 중복이었음 → 제거하고 `restore`·`bonusEffect`로 대체. `bonusEffect`를 `effect`와 별도 필드로 둔 이유는 "요리한 PC만 받음"이라는 룰적 제약이 명확하기 때문(F2 양도 로직에서 분기 기준이 됨).

## D21. 이니셔티브 — 민첩 직접 값, PC 동률 우선

**결정:** Combat 이니셔티브를 `@speed`로 설정. 다이스 굴림 없음(공식 룰: 능력치 비교). 동률 시 PC 우선만 자동 정렬(`AsterCombat#_sortCombatants`), PC끼리·NPC끼리는 GM 수동 조정.

**배경:** 룰적으로 이니셔티브는 다이스 굴림이 아니라 민첩 수치 비교다. 기존 코드의 `1d20 + @abilities.dex.mod`는 Foundry 보일러플레이트 잔재로 룰·시스템 모두와 무관(`@abilities`·`dex` 키 자체가 이 시스템에 없어 `1d20 + 0`으로 굴려지던 사이드 버그).

**대안:**

- 굴림을 유지하되 민첩을 보너스로 (`1d20 + @speed`) — 룰 위반
- Combat 표준 우회 (hook으로 직접 값 설정) — 코드 복잡도 증가
- 동률 완전 자동 (NPC 간도 임의 결정) — GM 재량 침해 (D12)

**선택 이유:** `@speed`는 Foundry 표준 `formula` 메커니즘 그대로 사용하면서도 다이스 없이 결정론적. 동률 처리는 룰이 명시한 부분(PC 우선)만 자동화하고 사람 판단 영역(의논·자유 결정)은 미개입 — D12 자동화 경계 원칙 일관. PC끼리/NPC끼리 동률은 `_sortCombatants`가 0을 반환해 `Array.sort`의 안정성으로 기존 순서 보존.

`system.speed`는 D15(derived) + D16(Active Effect ADD)으로 피로 적용 후 최종값이 자동 반영됨. 이니셔티브가 별도 계산 없이 그 값을 그대로 받는다 — D15·D16의 회수.

> **명세 정정 — `@system.speed` → `@speed`:** 명세는 `@system.speed`를 1순위로 제시했으나, `actor.getRollData()`가 `system`의 키를 **최상위로** 펼쳐 반환(이 시스템의 `_getCharacterRollData`가 `data.abilities`·`data.attributes.level`를 최상위로 접근하는 것이 증거)하므로 `@system.speed`는 `rollData.system.speed`(undefined)를 찾아 조용히 0이 된다. 실측 결과 `@speed`가 정답. 명세도 이 가능성을 확인 항목으로 명시했음.

> **NPC speed:** NPC DataModel에 `speed` 필드 추가(GM 수동 입력, initial 0). NPC 시트는 현재 미정비 boilerplate(`system.power`·`system.xp` 등 미존재 필드 참조)라 입력 UI는 후속 트랙으로 분리 — GM은 Combat Tracker에서 이니셔티브를 직접 편집하거나 콘솔로 speed 설정 가능.

> 라운드별 재이니셔티브(공식 룰의 미행동 PC 표현)는 G2에서 라운드 hook과 함께 처리 예정. 이번 STEP은 1회 결정만.

**갱신 (G1 보완 — 자동 적용 + UI 정리):** Foundry 기본 흐름은 "GM이 d20 아이콘 클릭 → 굴림 → 채팅 출력"이지만, 우리 시스템에서 이니셔티브는 다이스 굴림이 아니므로 클릭/채팅 단계가 룰 흐름에 없다. 이를 다음과 같이 정리:

- **자동 적용**: `createCombatant` hook으로 액터 추가 즉시 이니셔티브 = `system.speed` 자동 설정. GM만 처리해 중복 update 방지. 클릭 단계 제거. (D22에서 `combatStart`가 `_startRound`로 전체 이니셔티브를 갱신하게 되어, 기존 `combatStart` 누락-안전망은 그쪽에 포섭됨.)
- **채팅 억제**: `rollInitiative`를 거치지 않고 `updateEmbeddedDocuments`로 initiative를 직접 설정 — 채팅 메시지를 원천 차단. 결과는 Combat Tracker에서 직접 확인.
- **UI 정리**: Combat Tracker의 d20 굴림 컨트롤을 CSS로 숨김 — 클릭할 일이 없으므로 잘못된 신호 제거.

> **명세 정정 — `rollInitiative({createCombatMessage:false})` → 직접 update:** 명세는 `rollInitiative`에 `createCombatMessage:false`로 채팅을 억제하려 했으나, V13의 `rollInitiative` 옵션은 `{formula, updateTurn, messageOptions}`뿐이라 `createCombatMessage`는 무시되고 채팅이 그대로 출력된다(fvtt-types `InitiativeOptions`로 확인). 이니셔티브가 다이스 없는 결정론적 값(`system.speed`)이므로 `rollInitiative` 자체를 우회하고 `updateEmbeddedDocuments("Combatant", [{_id, initiative}])`로 직접 설정 — 채팅 차단이 보장되고 API 의존도 없다.

> 룰적으로 굴림이 아닌 경우, Foundry 기본 UI/메시지를 그대로 두면 PL이 "굴려야 하는가?" 혼동한다. UI는 룰의 동작 모델을 정확히 반영해야 한다 — 어떤 액션이 시각적으로 가능해 보이는데 의미가 없으면 인지 부담이 된다.

## D22. 전투 라운드 인프라 — 액션 포인트 + 이니셔티브 라운드별 갱신

**결정:** 매 라운드 시작 시 `AsterCombat#_startRound`가 (1) 모든 Combatant의 이니셔티브를 현재 `system.speed`로 갱신, (2) PC의 액션 포인트를 1d6 굴려 Combatant flag(`aster.actionPoint`)에 저장, (3) 라운드 시작 채팅 카드 출력. Combat Tracker 각 PC 행에 `renderCombatTracker` hook으로 AP를 표시.

**배경:** 공식 룰의 미행동 PC 전체가 능력치 비교는 라운드 사이에 민첩이 바뀔 수 있음을 전제(상태이상 적용/해제). 공식 룰의 매 라운드 굴림 액션 포인트도 라운드마다 갱신되는 임시 값.

**대안:**

- 액션 포인트를 actor DataModel 영구 필드로 (영구화 어색)
- 액션 포인트를 Active Effect로 (과한 추상화)
- 이니셔티브 갱신 안 함 (G1 1회 결정 유지, 룰 위반)
- 라운드별 처리를 `combatStart` 단일 hook에만 (라운드 2+ 갱신 불가)

**선택 이유:** Combatant flag는 (1) 라운드별 임시 값 의미에 정확, (2) 전투 종료 시 Combatant 삭제로 자동 정리, (3) Foundry 표준 API. 이니셔티브 갱신은 `_sortCombatants`와 결합해 매 라운드 자연스러운 재정렬을 만든다 — D16(Active Effect)가 변화한 민첩값이 즉시 반영. 채팅 카드는 PL이 자기 액션 포인트를 한눈에 보고 액션을 결정하도록 함(D12 — 액션 선택은 자동화 안 함).

> **명세 정정 — `_startRound`를 `combatStart` + `combatRound` 모두에 연결:** 명세 "권장 패턴"은 `_startRound`를 `combatRound`에만 연결하라 했으나, V13에서 라운드 1은 `combatStart`만, 라운드 2+는 `combatRound`만 발화한다(상호 배타적, fvtt-types `_RoundUpdateData` 주석이 두 이벤트를 구분). `combatRound`에만 연결하면 **라운드 1의 액션 포인트가 누락**되므로 두 hook 모두에 연결. 두 이벤트가 겹쳐 발화하지 않으므로 중복 굴림 없음. (명세도 이 가능성을 확인 항목으로 명시.)

> **AP 표시(STEP 2)의 DOM 의존성:** `renderCombatTracker`로 Combat Tracker 행에 AP를 주입하는 방식은 V13 버전별 DOM 구조(`.combatant`, `.token-initiative`)에 의존해 런타임 검증이 필요하다. 채팅 카드(STEP 1)가 AP 확인의 확실한 1차 수단이고, 트래커 표시는 보조 UX. 셀렉터가 안 맞으면 카드만으로도 기능은 성립한다.

> 라운드별 클린업(룰 593 "미행동 복귀")은 Foundry 표준 라운드 진행에 포함되어 별도 처리 불요.

## D23. 전투 부상/큰부상 자동 적용 — `_onEndTurn` 오버라이드 + `deleteCombat`

**결정:** 행동완료(턴 종료) 시점에 부상·큰부상에 따른 체력 차감 자동 적용. 전투 종료 시 큰부상 → 부상 전이. 건강 0 도달 시 채팅 안내만(D12 — 행동불능 자동 처리는 GM 판단). 부상 + 큰부상 동시 체크 시 둘 다 누적 적용(누적 차감, 사용자 확정).

**배경:** 관련 공식 룰의 부상/큰부상 효과는 명확한 트리거를 가짐. 라운드 인프라(D22) 위에서 자연스럽게 적용 가능.

**대안:**

- 트리거를 수동 버튼으로 (시트의 행동 종료 버튼) — 자동화 가치 낭비
- 부상·큰부상 적용을 Active Effect로 — "현재 건강에서 1회 차감"은 changes로 표현 어려움
- `combatTurn` hook + `combat.previous.turn` 인덱스로 직전 Combatant 재구성 (명세안)

**선택 이유:** V13이 제공하는 `_onEndTurn(combatant, context)` 오버라이드를 사용 — (1) 턴이 끝난 Combatant를 **직접 인자로** 받아 인덱스 재구성이 불필요하고(명세가 "까다롭다"고 우려한 부분 제거), (2) **단일 GM에서만 실행**되는 내장 가드가 있어 중복 update가 원천 차단되며, (3) 라운드 경계에서 **마지막 Combatant의 턴 종료도 누락 없이** 발화한다(`combatTurn` hook만 쓰면 마지막 턴→라운드 전환이 `combatRound`로 가 누락됨). 전투 종료는 `_onEndCombat`/`combatEnd` 훅이 없어 `deleteCombat`(전투 종료의 표준 경로)에서 처리.

기존 `_applyInjuryHealthLossIfExploration`(D19)을 일반화 — 코어 로직(`_applyInjuryHealthLoss`) 분리, 페이즈 체크는 외부 위임. DRY + 재사용. D11(관심사 분리) 회수.

> **명세 정정 — `combatTurn` hook → `_onEndTurn` 오버라이드:** 명세는 `combatTurn` hook에서 `combat.previous.turn`으로 직전 Combatant를 찾으려 했으나(스스로 "까다롭다" 표기), V13 `Combat`은 `_onEndTurn`/`_onEndRound`/`_onStartTurn` 같은 세분화된 오버라이드 포인트를 제공한다(fvtt-types 확인). `CONFIG.Combat.documentClass = AsterCombat`가 이미 등록돼 있어 오버라이드가 모든 전투에 적용되고, hook 등록·GM 가드·인덱스 계산이 전부 불필요해진다.

> **D16 AE 동기 연동:** `bigInj`/`injury` 변경 시 `_onUpdate`의 AE 동기화가 호출되나, 두 필드는 `BADSTATUS_EFFECTS` 정의가 없어(피로·졸림만 대상) no-op. 전이는 boolean만 바뀐다.

> 라운드 인프라(D22)의 자연 회수 — `AsterCombat`가 라운드 흐름 전반(정렬·이니셔티브·라운드 시작·턴 종료·전투 종료)의 룰 자동화 허브가 됨.

## D24. 전투 액션 UI — 서브 탭, 하이브리드 진입, 효과 자동화 점진

**결정:** character 탭 안 서브 탭으로 "combat" 추가(inventory·spell 옆, 항상 노출). 6종 액션 버튼(돌던지기/방어/집중/대쉬/차지/합체기 준비) — 단순 액션은 즉시 발동, 입력 필요 액션은 다이얼로그. 이번 STEP은 **AP 차감 + 채팅 출력**만 자동화. 룰의 다음 라운드 효과·라운드당 1회 제한·대미지 처리는 텍스트 안내로 PL/GM 수동 추적. NPC 시트는 서브 탭 자체가 없어 무영향(룰 590 — 액션 포인트는 PC 한정).

**배경:** 공식 룰에 정의된 6종 액션을 시트에서 선언·소비할 수 있어야 PL이 전투 흐름을 따라간다. 동시에 각 액션의 효과 자동화는 깊이가 매우 달라(대쉬는 다음 라운드 AE, 차지는 다음 라운드 AP 보정 등) 한 STEP에 다 담으면 분량이 폭발.

**대안:**

- 메인 탭에 "전투" 4번째 동급 탭
- 시트 첫 화면에 액션 영역 — 공간 부족
- Combat Tracker 확장 — V13 DOM 조작 깊어짐
- 채팅 매크로 — 시트 변경 없음
- 모두 다이얼로그(단순 액션도 확정 단계) — 마찰 큼
- 자동화 전체(G3-γ) — 분량 폭발

**선택 이유:** 서브 탭은 (1) PL이 액션 결정 시 능력치·상태이상·AP를 한 시야에서 본다, (2) 의미적으로 inventory·spell과 같은 "사용" 카테고리, (3) craft·record는 정적 정보라 메인 탭에 적합. 하이브리드 진입은 단순 액션 마찰을 최소화하면서 입력 필요 액션만 다이얼로그로 사용자 판단을 받음. 자동화 깊이는 G3-α(UI + AP 차감)로 시작하고, 효과는 PL/GM이 머리로 추적 가능한 범위로 둠(D12 자동화 경계). 채팅 카드에 "수동 처리" 문구를 명시해 한계를 인지시키고, 효과 자동화는 후속 STEP으로 점진(D13).

합체기 준비는 Combatant flag(`aster.unisonReady`)로 저장 — G4에서 "준비된 PC끼리 페어"로 활용.

> **AP 표시 동기화:** AP는 Combatant 문서의 flag이라 Actor 시트가 자동 갱신되지 않는다. `updateCombatant` hook으로 flag 변경 시 해당 액터 시트를 `render(false)` — 시트의 AP 표시를 Combat Tracker와 동기화. (실측으로 확인: Actor 시트는 Combatant 변경을 구독하지 않음.)

> **AP 부족 검사를 다이얼로그 입력 *후*에 둔 이유:** 대쉬는 입력값 X가 곧 비용이라 다이얼로그를 먼저 띄워야 비용이 확정된다. 취소 시 차감·채팅 모두 없음.

> 라운드 인프라(D22)·부상 자동화(D23)의 자연 연장 — 같은 Combatant flag 패턴(`actionPoint`, `unisonReady`)으로 상태 누적, 전투 종료 시 Combatant 삭제와 함께 자동 정리.

## D25. 캔버스 타게팅 — 사전 타게팅, 적 1체, 헬퍼 통일

**결정:** 돌던지기·마법·합체기 등 대상이 있는 액션에서 Foundry 표준 캔버스 타게팅(사용자가 사전에 Shift+클릭으로 토큰 지정)을 사용. 헬퍼 `getTargetedTokens`로 검증·반환 통일. 돌던지기는 적(NPC) 1체 필수, 마법은 선택적, 합체기는 G4에서 호출.

**배경:** G3-α의 돌던지기는 자유 입력 텍스트 다이얼로그였음 — (1) 입력 마찰, (2) 대상이 실제 토큰인지 시스템이 모름, (3) 향후 대미지 자동 적용 시 대상 식별 불가. Foundry 표준 타게팅(`game.user.targets`)으로 세 문제 모두 해결.

**대안:**

- 사후 타게팅(Crosshair, 액션 클릭 후 캔버스 클릭) — 직관적이나 코드 복잡 + 클릭 단계 추가
- 텍스트 입력 유지 — 빠르지만 검증 불가
- 토큰 ID 드롭다운 — 큰 시나리오에서 목록 폭발

**선택 이유:** 사전 타게팅이 UX·코드 모두 최적 — 사용자는 보통 액션 결정 *전에* 누구를 노릴지 정하고, `game.user.targets`는 한 줄로 접근 가능. 헬퍼로 검증 로직을 모으면 다른 액션·마법·합체기에 일관 적용(D11 관심사 분리). 검증 실패 시 경고 토스트 후 종료 — 자원 소비도 다이얼로그도 없음("잘못된 상태로 진행하지 않음"이 사용자 의도).

마법은 선택적 타게팅(옵션 B) — 자기 강화·아군 보조 마법까지 타겟 강제하면 어색. 마법별 "대상 필수" 분류(옵션 A)는 spell 데이터 모델 확장이 필요해 별도 STEP.

> **확인 항목 처리:** `game.user.targets`는 V13에서 `UserTargets`(Set 확장) — `Array.from`으로 토큰 배열화(fvtt-types 확인). 돌던지기 `allowedTypes:"npc"`는 공식 룰 단일 적에 충실 — PvP(character 적) 시나리오가 필요해지면 호출 측 옵션만 바꾸면 됨. 헬퍼는 Foundry 런타임 전역(`game.user`·`ui`)을 다루므로 순수 헬퍼 컨벤션과 달리 `@ts-check`를 생략(타입 체크 대상 외).

> 헬퍼는 합체기(G4)에서도 그대로 호출 가능 — 주공격 대상 1체, 부속성 효과 대상을 같은 함수로 처리. 코드 자산 재사용.

## D26. 회피 판정 메커니즘 — 별도 메서드 + 보정 context 인자

**결정:** `actor.rollDodge()` 메서드 신설. `computePenalties(actor, context)`에 context 인자 추가해 회피 판정에만 피로 -3 적용. 진입점은 combat 서브 탭. 회피는 대결판정이므로 기존 `vs` 카드 템플릿 재사용. AP 소비 없음(반응 판정).

**배경:** 공식 룰의 회피는 (1) ability가 아닌 derived 값(`system.dodge`, D15) 기반, (2) 피로 시 추가 보정이 회피에만 적용. `rollAbility`로는 두 특수성을 자연스럽게 표현 불가.

**대안:**

- `rollAbility`에 "dodge" 의사 ability 키 추가 — 분기 폭증
- `computeDodgePenalties` 별도 함수 — 보정 계산 분산
- 피로 보정을 호출처에서 직접 가산 — 보정 일원화 원칙(D11/D18) 깨짐
- 진입점을 character 탭 dodge 옆에 — 룰적으로 회피는 전투 행동이라 combat 탭이 자연스러움

**선택 이유:** `rollDodge` 별도 메서드는 회피의 특수성(파생 값·피로 보정·대결판정 강제)을 명확히 분리. `computePenalties`에 context 인자 추가는 보정 계산을 한 함수에 모으면서 회피/일반 분기를 표현(D11 유지, 시그니처만 확장). 호출자가 `{ isDodge: true }`로 의도 표현.

졸림 자동 해제·포만 자동 감소는 회피에서 호출 안 함 — 회피의 성공/실패는 대결 결과로 결정되어 호출 시점에 미정(졸림 해제 보류), 공식 룰의 전투 중 처리 제외(포만 미호출).

> **명세 정정 — 피로 필드는 `fatigue`가 아니라 `exhaustion`:** 명세는 `badstatus.fatigue`로 가정했으나 실제 DataModel·i18n 필드는 `exhaustion`(= "피로"). penalty 객체 키도 기존 컨벤션(키 = 소스 필드명: `sleepy`←`badstatus.sleepy`, `satiety`←`satiety`)에 맞춰 `exhaustion`으로 통일. 카드 표시는 기존 `ASTER.badstatus.exhaustion`("피로") 키 재사용 — 새 i18n 키 불필요. 명세가 확인 항목으로 표시한 부분.

> D18(penalties 통합)의 두 번째 회수 — context 인자로 시그니처 확장. 향후 다른 보정 컨텍스트도 같은 패턴 가능.

## D27. 대미지·상태이상 적용 — 채팅 카드 GM 버튼, 회피는 수동

**결정:** 돌던지기·마법 카드에 GM 전용 "대미지 적용" 버튼 추가. 클릭 시 다이얼로그(대미지 수치 + 상태이상 체크박스 5개) → 대상 액터 건강 -N + 상태이상 부여 자동. 돌던지기는 기본 수치 자동 추출, 마법은 GM 입력. 회피 결과는 GM 판단(회피 성공 시 버튼 안 누름).

**배경:** 캔버스 타게팅(D25)으로 대상이 정확히 식별되고 회피(D26)가 갖춰진 직후, 대미지 적용 자동화가 자연스러운 다음 단계.

**대안:**

- 대상 시트에서 "대미지 받기" 버튼 — 공격자 카드와 분리, 컨텍스트 손실
- GM 패널 통합 대미지 액션 — 대상 식별을 매번 입력
- 회피 자동 결합 — "최근 회피" 정의 모호
- 마법 대미지 자동 추출(데이터 모델 확장) — 분량 폭증, 별도 STEP
- 상태이상 미포함 — 같은 결과 처리를 분리하면 사용성 저하

**선택 이유:** 채팅 카드 버튼은 (1) 공격자→대상 흐름이 한 카드에서 닫힘, (2) 기존 패턴(피크닉·대성공 후속·대결 결합)과 일관, (3) flag로 중복 방지·대상 식별 보존. 돌던지기 자동 추출은 룰 명시(기본 수치). 마법은 효과문이 자유 텍스트라 자동 추출 불가 → GM 입력으로 시작, 데이터 구조화는 별도 STEP. 회피는 GM이 버튼을 안 누르는 단순 흐름(D12 자동화 경계). 상태이상은 다중 선택(마법 효과문의 다중 부여 케이스 대비), 부여만 처리(회복은 별도).

> **명세 정정 — 피로 체크박스는 `fatigue`가 아니라 `exhaustion`:** 명세 다이얼로그는 `value="fatigue"` + `ASTER.badstatus.fatigue`로 작성됐으나, 실제 badstatus 필드는 `exhaustion`이고 i18n 키도 `exhaustion`("피로")이다(D26과 동일 정정). 또 필드명↔i18n 키 불일치(`bigInj`↔`biginj`)를 `DAMAGE_STATUSES` 매핑 테이블로 일원화해 체크박스·결과 카드 양쪽에서 재사용.

> **체크박스 수집:** `form.querySelectorAll('input[name="status"]:checked')`로 수집 — NodeList/단일 요소 분기 우려를 원천 제거(D25 타게팅에서 쓴 패턴과 동일).

> **flag 키 분기:** 돌던지기는 `combatAction`, 마법은 `spellCast` flag에 대상 정보 저장. 한 카드에 둘 중 하나만 존재하므로 `combatAction ?? spellCast`로 단일 핸들러가 양쪽 처리. 중복 방지는 해당 flag의 `damageApplied` 토글.

> D16(Active Effect 자동 동기)의 회수 — 상태이상 boolean 갱신 시 피로(민첩 -3)·졸림(달성치 -2) 등 AE가 자동 적용. hook 한 곳에 처리가 모임.

## D28. resolveOpposed 회피 인지 강화 — 결과 카드에 대미지 버튼 연결

**결정:** `opposedRoll.isDodge` flag를 기반으로 resolveOpposed 결과 카드가 회피 승패를 인지. 회피 패배 시 "대미지 적용" 버튼 표시(GM이 수치·상태이상 입력), 회피 승리 시 "회피 성공 — 무효" 라벨 표시(버튼 미표시). 회피 미포함 대결판정은 기존 동작 유지(라벨·버튼 없음).

**배경:** D26(회피)와 D27(대미지 적용) 두 메커니즘이 갖춰졌으나 분리된 흐름이었음 — GM이 회피 결과를 보고 공격 카드로 돌아가 수동 적용. resolveOpposed 마무리에서 두 흐름을 연결해 GM 인지 부담을 줄임.

**대안:**

- 대미지 적용 시 회피 자동 탐색 — "같은 라운드 회피" 정의 모호, 알고리즘 복잡
- 회피 결과 카드에 표시만(버튼 없음) — 자동화 가치 작음
- 공격 종류 자동 추출(attackType flag) — 돌던지기만 가능, 나머지는 결국 GM 입력
- 단일 헬퍼 일반화 — 시그니처 복잡화(opposedResult flag와 combatAction/spellCast flag는 구조가 다름)

**선택 이유:** (1) GM이 이미 짝짓는 흐름(resolveOpposed)의 자연 연장, (2) 회피 카드의 `isDodge` flag만 보면 결과 분기 가능, (3) 자동 추출 없이 GM 입력으로 시작해도 공격 종류별 대미지 차이를 GM 판단으로 처리. 회피 승리 시 버튼 미표시(라벨만)는 공식 룰 정합 — 회피 성공 시 효과 자체가 발생 안 하므로 GM 오적용 차단.

> **헬퍼 분리:** 새 진입점 `applyDamageFromOpposed`(opposedDamage flag 기반)를 `applyDamageFromCard`(combatAction/spellCast flag 기반)와 별도 함수로 분리 — flag 데이터 구조가 다르고 검증 분기(noTarget 체크 유무)도 다름. data-action도 `apply-damage-opposed`로 구분해 두 hook이 독립 동작.

> **공통 로직 추출 — DRY:** 다이얼로그(`promptDamageDialog`)·건강 차감+상태이상(`applyDamageAndStatus`)·결과 카드(`renderDamageResultCard`)를 3개 헬퍼로 추출. `applyDamageFromCard`/`applyDamageFromOpposed`가 동일 함수를 호출해 본문이 진입점별 검증·flag 갱신만 남음. 향후 진입점(합체기 등)에서도 재사용. D11(관심사 분리)의 누적 회수.

> **flag null 분기:** `opposedDamage` flag는 회피 패배 시에만 생성, 회피 승리·미포함은 `null`. 버튼이 템플릿(`dodgeLost`)에서만 렌더되고 핸들러도 flag null 체크로 이중 방어. 중복 방지는 `damageApplied` 토글(D27과 동일).

## D29. 마법 데이터 모델 확장 — 대미지·상태이상·대상 필수

**결정:** `spell.system`에 `damage: number`, `inflictStatus: string[]`, `requiresTarget: boolean` 세 필드 추가. 마법 사용 시 시스템이 이 필드들을 읽어 `spellCast` flag에 자동 저장, 대미지 적용 다이얼로그에서 기본값으로 채움. 효과 자유 텍스트(`effect`)는 그대로 유지 — 구조화 필드는 자동 처리 보조 정보.

**배경:** D27(대미지 적용)에서 마법은 GM 입력으로 시작했음. 마법 효과를 데이터 모델 차원에서 구조화하면 (1) GM 입력 부담 감소, (2) 같은 마법 반복 사용 시 입력 일관성, (3) 향후 효과 자동 적용(회복 등) 확장 기반.

**대안:**

- 옵션 A: damage만 추가 — 상태이상 부여 빈도가 높아 보조 가치 누락
- 옵션 C: 회복·보정 등 다양한 효과 — 분량 폭증, 시트 UI 복잡 (별도 STEP)
- 옵션 D: 효과 객체 배열(`effects: [{type, value}]`) — 처음부터 복잡, 데이터 변환 비용
- 자유 텍스트 그대로 — 매번 GM 입력 부담

**선택 이유:** 옵션 B(damage + inflictStatus + requiresTarget)는 (1) 룰적으로 빈도가 높은 두 효과(대미지·상태이상 부여)에 집중, (2) 시트 UI 추가 부담 작음, (3) D27의 `defaultDamage`/`defaultStatus` 패턴 그대로 활용, (4) 효과 자유 텍스트를 보조로 유지해 공식 룰 자유 표현 보존. `requiresTarget`은 CANVAS_TARGETING(D25)에서 보류한 "마법별 대상 필수" 분류의 자연 회수 — 데이터 모델 확장하는 김에 같은 시트·핸들러를 한 번에 처리.

> **상태이상 키 단일 소스:** 명세는 `DAMAGE_STATUSES`(aster.mjs)와 spell `choices` 두 곳에 5개 키를 중복 나열하는 구조였으나(드리프트 위험을 확인 항목으로 명시), `config.mjs`에 `DAMAGE_STATUSES` + 파생 `BADSTATUS_KEYS`를 단일 소스로 추출해 양쪽이 같은 출처를 참조하도록 통일. 2곳 이상 실제 재사용이라 추출이 정당(조기 추상화 아님). `choices` 제약으로 잘못된 키 저장도 DataModel이 차단.

> **마이그레이션 불요:** DataModel `initial`로 기존 spell에 새 필드 자동 채움 (food 패턴, D20). 명시 마이그레이션 함수 없음.

> **명세 정정 — `_processFormData`가 아니라 `#onSubmit`에서 배열 변환:** 명세는 다중 체크박스→ArrayField 저장을 `_processFormData` 오버라이드(방법 A)로 제시했으나, 이 시트는 커스텀 폼 핸들러(`forms.handler = #onSubmit`)를 쓰므로 DocumentSheetV2의 기본 제출 경로(`_processFormData`)가 **호출되지 않는다**. 오버라이드는 dead code가 됨. 따라서 핸들러(`#onSubmit`) 안에서 `form.querySelectorAll('input[name="system.inflictStatus"]:checked')`로 명시 수집 — 전부 해제 시 `[]` 보장(FormDataExtended의 단일/배열 처리에 비의존). `includes` Handlebars 헬퍼는 부재해 `_prepareContext`에서 `spellInflictFlags` 사전 계산 + 기존 `checked` 헬퍼 사용(사용자 메모리의 "헬퍼 부재 → 컨텍스트 사전 계산" 패턴 일관).

> **자동 추출은 기본값이지 강제 아님:** spellCast flag의 `defaultDamage`/`defaultStatus`는 다이얼로그 초기값일 뿐 GM이 조정 가능(D12 자동화 경계). `requiresTarget: true` 마법은 타겟 없으면 시전 자체 취소(자원 소비 전 검증) — 자기 강화 마법(`false`)은 타겟 없이 진행. 전투 종별(`actionType`)·회복 효과는 별도 STEP.

## D30. 자동화 도달점 — 점진 도달, D&D 완전 모델은 의도적 미선택

**결정:** 마법·액션 효과의 자동화를 점진적으로 확장하되, D&D 5e 시스템처럼 **모든 효과를 데이터 카테고리로 구조화해 AE로 자동 적용**하는 완전 모델은 의도적으로 선택하지 않음. 대신 *결과 자동 추출* + *일회성 효과 만료 자동화* + *명확한 회복 효과 자동화*까지의 80~90% 도달점에서 멈추고, 남은 자유 표현 효과는 텍스트 + GM 수동 처리를 유지.

**배경:** 마법 데이터 모델 확장(D29) 진행 중 자연스럽게 떠오른 질문 — "장기적으로 D&D처럼 effect를 description으로 두고 별도 시트로 효과를 정의해 AE로 구현하는 게 가능한가, 비용이 맞는가". 평가가 필요한 분기.

**대안:**
- **A. D&D 완전 모델 도입** — 효과 카테고리 데이터 스키마 + 카테고리별 자동 적용 핸들러 + duration 시스템 + 라운드 만료 hook + 임시 AE 헬퍼 + 시트 입력 UI. 새 트랙 5~8 STEP 규모.
- **B. 완전 수동 유지** — 마법 효과는 자유 텍스트, 모든 적용은 GM 수동.
- **C. 점진 도달 (선택)** — 빈도 높은 효과부터 데이터화, 80~90% 도달 시점에서 만족.

**선택 이유:**

마기사의 마법 수가 D&D 대비 적고 공식 룰 효과 표현이 자유 서술 위주라, D&D 모델의 ROI가 낮다. 공식 룰 효과 중 *카테고리화 자체가 어려운* 케이스가 다수 있음 — 특정 효과의 자유 표현의 "다음 판정"이 몇 회까지인가, GM 판단형 표현 같은 자유 형태, 시나리오별 특수 효과 등. 카테고리 외 효과를 자유 텍스트로 두면 결국 *부분 자동화*가 되어, 사용자가 두 가지 입력 방식(데이터 + 자유 텍스트)을 모두 관리해야 함.

D&D 5e 시스템의 스펠 시트는 시전시간·범위·지속시간·컴포넌트·액티비티·스케일링 등 복잡도가 높음. 마기사 시나리오 작성자가 *시스템 개발자 수준의 이해*를 갖춰야 하는 진입 장벽. 완전 자동화는 *입력 부담* 자체가 채택 저항을 만듦.

반면 인프라는 이미 갖춰져 있어 점진 확장은 비용 작음:
- D11(순수 함수) → 효과 카테고리별 핸들러 깔끔히 분리 가능
- D16(AE 단방향 동기) → 같은 패턴 확장
- D17·D22(라운드 hook) → duration 만료 진입점
- `applyDamageFromCard`/`applyDamageFromOpposed`/`promptDamageDialog` → 효과 적용 패턴 정착
- D8(definition-driven) → 효과 카테고리 정의 한 줄 추가로 확장 가능

이 자산들은 *완전 모델 없이도* 80~90% 자동화를 가능하게 함. 룰 정합 명확한 효과만 점진 자동화하고, 자유 표현은 의도적으로 자유 텍스트 유지 — 공식 룰의 표현력 보존 + GM 재량 영역 침해 안 함(D12 일관).

**점진 회수 로드맵 (가이드라인, 강제 아님):**

1. **결과 자동 추출 (D29 진행 중)** — `spell.damage`, `inflictStatus`, `requiresTarget`. 가장 빈도 높은 두 결과(대미지·상태이상 부여) 자동.
2. **일회성 효과 만료** — G3-β 영역. 집중 +1d6·대쉬 민첩 +X·차지 등 *액션* 효과를 1라운드 만료 AE로. 마법은 자유 텍스트 유지.
3. **명확한 회복 효과** — `healHealth`, `restoreSatiety`, `cureStatus[]` 등. 특정 효과 결과·consumable 등 카테고리 명확한 회복만.
4. **여기서 만족** — 남은 자유 표현 효과는 텍스트 + GM 수동. 추가 자동화는 *구체적 빈도 통계*가 필요성을 입증할 때 결정.

**의도적 미선택 항목 (D&D 완전 모델 대비):**

- 효과 카테고리 강제 분류 (모든 효과를 데이터화)
- 시전시간·범위·지속시간 같은 D&D식 메타데이터
- 시나리오 작성자용 복잡한 효과 빌더 UI
- 스크립트 입력란 fallback (자유 텍스트로 충분)

## D31. G3-β 라운드 1회 제한 + 방어 차감 자동화

**결정:** Combatant flag `aster.actionsThisRound = { defend, charge }`로 라운드별 액션 사용 카운터 관리. `_startRound`에서 빈 객체로 초기화. 방어 사용 시 `aster.defendActive: true` 추가 → 다음 대미지 적용 시 1d6 굴림·차감·flag 해제 자동. 차지 사용 시 선택(`"ap"` | `"unison"`)을 `aster.chargeNextRound` flag로 저장(G3-γ 회수 대상). 사용된 액션 버튼은 시트에서 disabled + 시각 표시.

**배경:** G3-α에서 6종 액션의 UI·AP 차감까지 완료, 룰의 "1라운드 1회" 제한과 "다음 받을 대미지 -1d6" 효과는 *수동 추적* 안내문으로만 명시. D30 자동화 도달점 정책의 2단계(일회성 효과 만료) 진입 — 가장 빈도가 높고 룰 정합 명확한 두 효과부터 자동화.

**대안:**
- 옵션 A: 각 액션별 별도 flag (defendUsedThisRound, chargeUsedThisRound) — 액션이 늘 때마다 flag 증가
- 옵션 나: 방어 차감을 GM 수동 — 자동화 가치 누락
- 옵션 다: 방어 차감 미도입, "방어 사용 중" 표시만 — 룰의 명확한 결과 자동화 안 함
- 옵션 Y: 차지 선택을 이번 STEP에 저장 안 함 — G3-γ에서 다시 설계 부담

**선택 이유:** `actionsThisRound` 객체(옵션 B)는 향후 다른 액션이 비슷한 제한을 가질 때(예: "라운드 2회까지") 같은 구조 확장 가능 — D8(definition-driven)과 동일한 정신. 방어 차감 자동화(옵션 가)는 D30 1단계 "결과 자동 추출" 정책 정합 — 1d6 굴림 결과가 명확한 차감으로 이어지므로 시스템이 처리. 차지 선택 저장(옵션 X)은 한 줄 추가로 G3-γ 구현 비용을 미리 줄임.

방어 차감은 `amount > 0`일 때만 적용 — 상태이상만 부여하는 경우 방어 효과 미소비(룰 "받을 대미지" 정합). 차감 후 결과는 `Math.max(0, ...)`로 음수 방지.

`applyDamageAndStatus` 헬퍼(D27)에 방어 처리를 *통합* — `applyDamageFromCard`/`applyDamageFromOpposed` 두 진입점 모두 자동 적용. 진입점별 별도 처리 없음(D11 관심사 분리 + DRY).

> D27의 자연 회수 — 공통 헬퍼에 한 가지 효과만 추가하면 모든 대미지 진입점이 자동 갱신. 그동안 누적된 helper 분리가 이번 STEP의 비용을 크게 줄임.
>
> D30의 2단계 시작 — 향후 G3-γ가 차지 효과(차지의 다음 라운드 효과) 적용을 라운드 hook에 추가하면 2단계 완성.

## D32. 인라인 카드 → 템플릿 분리 (H 트랙 사전 정리)

**결정:** D24(COMBAT_ACTION_G3A)·D27(DAMAGE_APPLY)에서 인라인 문자열로 생성되던 채팅 카드 2종(`combat-action-card`, `damage-result-card`)을 `templates/chat/*.html` 파일로 분리. JS는 `renderTemplate`으로 호출. 향후 H 트랙(디자인 정리)의 사전 정리 성격.

**배경:** D24·D27 적용 시 카드 구조가 단순하고 빠른 구현이 우선이었기에 JS 안의 문자열로 생성했음. 결과로 SCSS 변경 시 인라인 카드의 클래스명·구조 동기가 수동으로 필요 — 향후 H1(채팅 카드 일관성 통일)에서 *변경 누락 위험* 발생.

**대안:**
- 가이드만 명시, 코드 변경 0 — 코드 자산 분리 가치 미회수
- H1 시점에 한꺼번에 분리 — H1 분량 증가 + 다른 정책 결정과 섞임
- 사전 정리 STEP (선택) — *코드 분리만* 미리, *디자인 정책*은 H1로 미룸

**선택 이유:** 사전 정리는 *디자인 결정 없이 코드 구조만* 정리 가능 — H1에서 디자인 정책 결정 후 *템플릿 한 곳만 수정*하면 모든 카드에 자동 적용. 분량 작고(STEP 1~2 두 카드, 추가 발견 시 옵션) 회귀 검증 단순(클래스명 동일, 출력 결과 동일).

추가 인라인 카드(라운드 시작·부상·전투 종료·장면 이동) 분리는 *분량 판단 후 별도 STEP*으로. 한 커밋에 너무 많은 카드 변경은 회귀 검증 부담.

> H 트랙의 첫 진입. 디자인 정리는 *별도 트랙*으로 자리잡고, 사전 정리는 *기능 트랙에서 자연스럽게* 가져갈 수 있음을 보여준 케이스. D11(관심사 분리) 원칙의 점진 회수 — 결합되어 있던 *JS 로직 + HTML 마크업*을 분리.

## D33. G3-γ 다음 라운드 효과 자동 적용 — 집중·대쉬·차지(AP)

**결정:** G3-α의 액션 효과 중 다음 라운드/판정에 작용하는 세 가지를 자동화. 집중은 Combatant flag `focusActive` → 다음 판정의 기본 굴림 수 증가 단순 합산, 적용 후 flag 해제. 대쉬는 사용 시 액터에 1라운드 만료 Active Effect 부착(`system.speed +X`), Foundry의 duration 자동 만료. 차지(AP)는 `_startRound`에서 `chargeNextRound === "ap"` 확인 후 추가 굴림으로 AP에 합산. 차지 합체기 효과는 G4 영역으로 유지.

**배경:** G3-α는 액션 UI + AP 차감까지 자동화하고 "다음 라운드 효과"는 *수동 처리* 안내문으로 남겼음. D30 정책의 2단계(일회성 효과 만료)를 완성하는 STEP. D31에서 방어·차지 사용 추적·차지 선택 저장 기반이 갖춰져 이번 STEP의 비용이 크게 줄음.

**대안:**
- 집중에 다이스 선택 다이얼로그(`pickDiceDialog` 재사용) — 판정 흐름에 다이얼로그 끼움, 사용성 저하
- 대쉬를 Combatant flag로 표현 후 라운드 hook에서 적용/제거 — Foundry AE 자동 만료 활용 못함
- 차지 합체기까지 같이 처리 — G4 미구현 상태에서 분기 정의 어려움
- 모든 효과를 한 메커니즘으로 통일 (예: 임시 AE) — 효과 성격이 달라 강제 통일 시 가독성 저하

**선택 이유:** 각 효과의 *룰적 시점 단위*가 달라 자동화 방식도 다른 게 자연스러움 — 집중은 "한 번", 대쉬는 "한 라운드", 차지 AP는 "다음 셋업 시점". 효과별로 적합한 패턴 사용. 집중의 단순 합산은 마법 추가 굴림(다이스 선택)과 다른 *판정 보정* 성격이라 다이얼로그 없이 자동 적용이 사용성·룰 정합 모두 자연스러움.

대쉬의 1라운드 만료 AE는 D16(Active Effect 단방향 동기)의 자연 확장 — 피로 AE와 같은 메커니즘이 *임시 효과*에도 적용됨을 확인. Foundry duration 자동 만료를 활용해 명시 정리 hook 불요.

차지 합체기는 G4 영역 — `chargeNextRound === "unison"`은 flag 유지. G4가 합체기 사용 시 이 flag를 읽어 다이스 +1d6 적용 후 해제. G3-α·D31·G3-γ 세 STEP에 걸쳐 *차지 선택 → 저장 → 사용*의 흐름이 분산. 코드 자산 누적의 좋은 사례.

> D30 정책의 2단계 *완성* — 일회성 효과 만료 자동화 도달. 이후 회복 효과 확장(3단계)으로 진행.
>
> G3-α의 "수동 처리" 안내문이 채팅 카드에서 제거됨 — 이전 명세의 *과도기적 표현*이 자동화 완성으로 사라지는 사례. 결정 일지의 의미.
>
> 집중은 *정동판정*(rollEmotion)에는 적용하지 않음 — 룰적으로 특정 판정 종류는 보정 미적용. 회피(rollDodge)는 일반 대결판정의 한 종류로 해석해 적용. 회피 적용 범위는 룰 해석에 따라 후속 조정 가능.

## D34. G4 합체기 본체 — 페어 선언·주/부속성·다이스 합산·부속성 자동 적용

**결정:** combat 탭 "합체기 발동" 버튼으로 PL이 시작. 페어 선택(unisonReady 2인) → 주속성 선택 → 각자 1d6 굴림(차지 효과 있으면 추가 + pickDiceDialog) → 합산값 안내(주속성 표는 GM 수동) → 부속성 효과 4종 자동 적용(적/청/녹/황). 회피 불가·행동완료는 채팅 안내만. unisonReady·chargeNextRound 두 플래그 회수.

**배경:** G3-α의 unisonReady와 D31의 chargeNextRound: "unison"이 사용 대기 중. 합체기는 *PC 전용 특수 행동*으로 메커니즘 복잡도가 크지만, 누적된 코드 자산(applyDamageAndStatus, focusActive, 1라운드 AE, pickDiceDialog, getTargetedTokens, DAMAGE_STATUSES)이 이번 STEP의 비용을 크게 줄임. D30 정지점 도달 전 큰 작업.

**대안:**
- 옵션 A: GM 패널 진입 — PL 주도 흐름 손상
- 옵션 다: 주속성 표 자동화 — 공식 표 관련 자료 외부 자료라 시스템 자동 처리 어려움(저작권·맥락)
- 옵션 ii: 부속성 일부만 자동화 — 패턴 일관성 손상, 분량 차이 작음
- 옵션 X: 합체기 대상 회피 시도 시 시스템 차단 — 회피 메커니즘에 분기 추가 부담
- 옵션 1: 행동완료 자동 진행 — combatTurn hook 중복 발화 위험

**선택 이유:** 옵션 B(combat 탭 버튼)는 PL이 자기 시트에서 발동 → 페어·주속성 선택의 *능동적 선택*이 공식 룰 흐름과 일치. 주속성 표 수동(옵션 나)은 D30 정책의 *명확한 정지점* — 자동화 어려운 영역은 GM 판단으로 명시 분리. 부속성 4종 자동화(옵션 i)는 같은 패턴(대상 선택 → 효과 적용)이라 분량 차이 작고 일관성 큼.

신규 헬퍼 `applyCureStatus`는 D30 3단계(회복 효과 확장)의 *사전 회수* — 특정 효과 결과을 통해 회복 메커니즘이 시스템에 들어옴. 향후 consumable 회복 등에서 동일 헬퍼 재사용.

회피 불가·행동완료의 안내만 처리는 D12 자동화 경계 — 시스템 강제 시 *PL 의도와 다른 결과* 발생 가능(예: 같은 적이 다른 PC 공격에 회피해도 차단되어버림). 룰 인지는 텍스트로 충분.

같은 색 페어는 부속성 결정 불가로 차단 — 공식 룰의 부속성 결정 표현은 *서로 다른 색* 전제. 룰 정합이 모호한 영역이라 명시 차단으로 안전. 색 미설정 PC도 동일하게 차단.

> 누적 자산의 *집결점* — G3-α(unisonReady), D31(chargeNextRound), D27(applyDamageAndStatus·DAMAGE_STATUSES), D29(spell 데이터 패턴), D33(focusActive, 1라운드 AE), D25(getTargetedTokens), D16(badstatus AE 동기)이 모두 한 STEP에서 회수. D11(관심사 분리) 원칙의 누적 효과가 분량 큰 STEP을 가능하게 만든 사례.
>
> D30 정책의 2단계 ~ 3단계 *전이점*. 회복 헬퍼(applyCureStatus)로 3단계 시작.

> 색 라벨은 신규 `ASTER.color.*` 키 신설 대신 기존 `ASTER.aster.{red/blue/green/yellow/white}` (마법 카드 색 라벨)를 재사용. 키 중복 방지. 백(white) 부속성은 공식 자료에 별도 표가 없어 switch default로 부속성 효과 카드 라인 자체 생략(주속성 합산값만 안내) — 룰 해석 모호 영역의 안전 처리.

## D35. G4-α 주속성 표 표준 효과 — 적·청·녹 정형 범위 자동화

**결정:** `module/helpers/unison-table.mjs`에 `UNISON_TABLES` 상수로 합체기표(적·청·녹) 데이터 정형 범위 정의. `lookupUnisonEffect(color, total)`로 조회. 단일 적 타겟 영역은 캔버스 타게팅, 전체 적 영역은 Combat NPC 자동, 전체 아군 영역은 게임 PC 자동. 자동 적용 시점은 다이스 합산 직후, 부속성 다이얼로그 *전*. lookup 결과 null이면 자동 적용 안 함, 채팅 카드에 GM 안내. 특정 효과 결과·12+·특수 범위 하한 자해·실패 범위는 G4-β 또는 후속.

**배경:** D34 합체기 본체가 부속성 효과는 자동화했으나, *주속성 표*는 "GM 수동" 안내만 출력했음. 표 데이터가 정형 패턴(80%가 단순 대미지/회복)이라 자동화 가치가 큼. D30 3단계 회복 효과의 *완성점* — 특정 효과 결과(`applyCureStatus`)에 이어 청표(`applyHealHealth`)로 회복 두 진입점 확보.

**대안:**

## D37. G4-γ RollTable 통합 — 플레이버 텍스트 자동 출력

- 페이즈 판정: 명세 초안의 `game.combat?.started` 대신 *currentPhase === "exploration"* 채택 — 피크닉(D20)·포만 감소와 동일 신호로 일관, "탐색 중에만" 정책의 엄밀 해석

**선택 이유:** 옵션 A(탐색 중만)는 관련 공식 룰을 *엄격 분리* — 시스템이 룰 인지에 기여. "탐색 중"은 combat 트래커가 아니라 *currentPhase*로 판정해 D20 피크닉 선례와 통일했고, 그 결과 클라이막스 페이즈에서 공식 룰 차단 안내가 자연 연결된다. 옵션 가(전원 -2)는 공식 룰의 전체 대상 표현의 엄밀 해석 — 본인도 회복 대가로 부담. 옵션 X(PC 시트 진입점)는 행동불능 PC가 자기 시트에서 직접 신청 — PL 주도. 옵션 i(흐름 차단)는 룰 엄밀 + 동작 명확.

## D40. F1 전투 종료 자동 회복 + 회복 효과 차단 — 공식 룰 정합

**결정:** 공식 룰의 두 영역을 한 STEP에 묶음. (1) **회복 차단** — `applyHealHealth`에 단일 분기 추가: climax 페이즈 + 건강 0 PC는 회복하지 않고 결과 객체에 `blocked: true` 반환. 호출자(R1 consumable, 특정 색 결과 표 (정형 + 특수))가 카드에 차단 안내. 상태이상 회복(`applyCureStatus`/`applyCureAllStatus`)은 차단하지 않음(공식 룰 체력 회복 효과만 명시 — 엄밀 해석). (2) **전투 종료 자동 회복** — `Combat._endCombat()`(deleteCombat hook, D23 큰부상→부상 전이와 동일 지점)에서 건강 0 combatant를 건강 1로 자동 회복 + 안내 카드.

**배경:** R2(탐색 중 협력 회복)가 공식 룰 중 *탐색 영역*만 다뤘고, F1이 *전투 중·전투 종료* 나머지 영역을 완결. 공식 룰의 한 조항을 R2(탐색)·F1(전투)로 페이즈 분할 자동화.

**대안 / 실측 정정:**

- 자동 회복 트리거: 명세 초안은 *페이즈 전이(climax→other)* 추정이나, 실측 결과 D23 전투 종료 흐름은 **`deleteCombat` → `Combat._endCombat()`**. 정책(옵션 D: D23 흐름 통합)을 살려 실제 발화 지점인 `_endCombat()`에 통합 — 부상 전이와 *같은 루프·같은 트리거*로 일관.
- 자동 회복 대상 범위: 명세는 `game.actors` 전체 PC, 실제는 D23과 동일하게 **`this.combatants`** 순회(전투 참가 PC) — 공식 룰의 전투 중 행동불능 상태 정합 + D23과 스코프 일치.
- 자동 회복 카드: *별도 템플릿 + `gm.systemSpeaker`* 대신 **인라인 HTML + 기존 `ASTER.combat.tracker` speaker** — `_endCombat`의 형제 카드(combat-end-card)와 동일 관례, 파일 내 일관성 우선(combat.mjs 카드는 모두 인라인).
- 차단 위치: 옵션 가(`applyHealHealth` 단일 분기) 채택 — 호출자마다 사전 검사(옵션 나)하면 중복. 진입점이 늘어도 자동 적용(D11 회수).
- 해석 2(상태이상도 차단): 룰 명시를 벗어난 과도한 해석 — 미채택.

**선택 이유:** `applyHealHealth` 단일 분기는 R1·합체기·향후 진입점 *모두 자동 적용*. `blocked` 선택 필드는 *기존 반환 형태 보존*(미설정 시 기존과 동일) — 회귀 안전. 차단 판정은 R2와 동일하게 climax 페이즈 신호 사용, 자동 회복은 D23과 동일하게 deleteCombat 이벤트 — 각 질문(상태 vs 이벤트)에 맞는 신호를 따로 선택. 특정 회복 효과 결과는 PC별 부분 차단 가능(행동불능 PC만 차단, 나머지 정상 회복) — 카드 한 줄 렌더를 `healLineFor` 헬퍼로 통합(heal·heal-and-cure-all 공용).

> F 트랙(룰 정합 마무리) 시작점. R2+F1로 공식 룰의 한 조항을 두 페이즈로 분할 자동화 완성 — 페이즈 시스템(D19)의 전체 활용 가치 증명. 다음은 F2(포만 관련) 또는 I 트랙(아이템 시트 정리).

## D42. I1b food 한 번에 하나씩 — 하드 차단 → 교체 다이얼로그

**결정:** food 1개 제약을 *하드 차단*에서 *교체 확인 다이얼로그*로 전환. 기존 `preCreateItem` 싱글톤 hook(`SINGLETON_TYPES=["bag","food"]`)을 수정 — food면 차단(`false`) 후 비동기 `promptFoodReplace`를 띄워 PL이 교체 여부 결정. 확인 시 기존 food 삭제 → 신규 재생성(삭제→생성 순서라 잠시도 2개 없음). bag은 기존대로 하드 차단 유지.

**배경:** 사용자 명시 — 특정 카테고리 아이템은 1개만 소지. 시스템엔 이미 food 싱글톤 차단이 있었으나, 추가 시도가 *조용히 거부*되어 PL이 교체 의도를 표현할 수 없었음.

**실측·기술 정정:**

- **명세의 async preCreateItem은 동작하지 않음**: preCreateItem 반환값은 *동기*로 검사 — `Promise`를 반환하면 truthy라 생성이 취소되지 않는다. 기존 코드도 그래서 *동기 차단*만 사용. 따라서 명세의 "hook 안에서 await 다이얼로그 → false 반환" 패턴은 불가.
- **채택 패턴**: 동기로 차단(`false`)한 뒤 다이얼로그를 *fire-and-forget*(`void promptFoodReplace`)로 분리. 확인 시 `existing.delete()` → `createEmbeddedDocuments([newData])`. 재생성이 preCreateItem을 다시 발화하지만 기존이 이미 삭제돼 통과 — 무한 루프 없음.
- 신규 데이터는 `item.toObject()`에서 `_id` 제거 후 재생성(새 인스턴스).

**대안:**
- 옵션 A (자동 교체, 확인 없음): 실수로 기존 food 분실 위험 — 미채택
- 옵션 B (createItem 사후 정리): async 자연스럽지만 *잠시 2개 상태* 발생, 명세가 무결성 이유로 거부 — 미채택. 동기 차단+재생성이 2개 상태를 원천 차단

**선택 이유:** 동기 차단 + 비동기 재생성은 명세 의도(2개 동시 없음 + PL 확인)를 *실제 동작하는 형태로* 달성. R2 다이얼로그 패턴(인라인 HTML + `DialogV2.confirm` + `.catch(() => false)`) 재사용으로 일관성. 기존 싱글톤 hook을 *확장*해 food만 분기 — bag 동작 보존.

> I 트랙의 작은 기능 영역. 다음은 I1c(equipment 시트 + 장비란 표시) — I 트랙 최대 영역.

**실측 정정 (명세 코드 오류 수정):**

- **자원 경로**: 명세는 `actor.system.material.value` / `actor.system.aster.red`였으나 실제는 `actor.system.material`(스칼라) / `actor.system.aster.{color}.value`(SchemaField). validateCraft·craftItem 모두 정정.

- craft-item.mjs는 actor 문서를 다뤄(아스테르·material 접근) `@ts-check` 미적용 — actor-sheet/aster 관례와 일치.

**대안:**
- 옵션 B (생성 + 시드 compendium 동시): xlsx가 그리드라 자동 추출 난도 높음 — 별도 트랙 분리

- craftRequires 자유 텍스트: 자동 검증 불가 — 정형 Object 채택(단, C1은 PL이 JSON 직접 입력, 드롭다운 UI는 C3로 미룸)

**선택 이유:** craft 탭 진입점은 설비 취득(D14)과 *같은 자리* — 룰북 공방 사용 PL 주도 정합. 드래그+자동 채움은 *재사용 + 커스텀 자유* 동시 지원, 향후 시드 compendium의 템플릿 활용으로 자연 확장. `craftRequires: Object`는 `prereqMet`의 base+level 매칭 패턴과 일관. D14 음수 허용 정책 재사용으로 *두 곳 다른 정책*의 모호함 회피.

## D45. C2 시드 아이템 compendium pack — 저작권 보호 + 빌드 인프라 공개

**배경:** C1 craft 메커니즘 완성 후 룰 자료(xlsx→JSON 추출)를 *어떻게 관리·배포*할지 결정. Aster는 팬 메이드 비공식 시스템·라이선스 없음 — 자료 공개 시 저작권 위험.

**대안:**
- A. 전체 GitHub 공개(D&D SRD 패턴): 라이선스 없는 비공식엔 부적합, 저작권 통고 위험 실재(WFRP4e 사례)
- B. LDB만 공개·JSON 비공개: 법적 차이 없음(저작권은 형식 아닌 내용) — 바이너리는 난독화일 뿐
- C. 시스템·콘텐츠 2 repo 분리(Foundry 표준): 안전하나 관리 부담, 작은 프로젝트엔 과함

**실측 정정 (명세 v3 가정 vs 실제 빌드 구조):**

- **출력 경로**: 명세는 `packs/items-*/` 격리였으나 실제 빌드는 **`dist/packs/`** 출력(이미 dist/ 무시) — `.gitignore`는 소스만 격리하면 충분.
- **자료 위치·보호 정정**: 실제 추출 자료는 `packs/_source/items/`(하위 디렉토리)에 있는데 기존 패턴 `packs/_source/items-*.json`는 *루트 직속만* 매칭해 **하위 디렉토리가 미보호**(git add 시 노출 위험)였다. `packs/_source/items/` 격리 추가로 차단. 빌드는 *하위/평면 두 배치 모두* 인식.
- **소스 형식**: 기존 unison-tables는 *dir-of-files*, 추출 자료는 *단일 JSON 배열* — 아이템 pack은 배열을 읽어 staging에 풀고 `!items!<id>` 키 주입 후 `compilePack`.
- **빈 소스 처리**: skip(경로 없음) 대신 *빈 LevelDB 생성* — manifest path가 항상 유효해 Foundry가 빈 compendium을 안정적으로 노출(빌드에서 검증).
- `.gitkeep` 불필요 — `packs/_source/`는 unison-tables로 이미 추적됨.

**선택 이유:** CoC7 패턴은 비공식·무라이선스 케이스의 보편적 안전형. 빌드 인프라는 *일반 JSON→LevelDB 변환 도구*라 룰 자료가 아님 → 공개 안전. `system.json` pack 경로는 *디렉토리 메타데이터*라 내용 없으면 저작권 무관. 단일 repo 유지로 관리 부담 최소화. *공개 인프라 / 비공개 자료* 분리가 향후 유사 자료(룰표·시나리오)에도 재사용 가능한 원칙.

> craft 트랙 기능 완비(C1 메커니즘 + C2 인프라). 시스템 메커니즘 구현은 *룰 동작 구현*이라 공개 안전, 자료 데이터는 *룰북 내용 자체*라 비공개 — 이 분리가 핵심.

## D47. N1 NPC DataModel 확장 + 기본 시트 — 자동화 헬퍼 재활용 기반

**결정:** NPC DataModel에 *식 능력치 3종*(`hitFormula`/`dodgeFormula`/`apFormula`, StringField), *AP 현재 상태*(`ap.value`/`ap.max`), *상태이상*(`badstatus`, PC와 동일 5종) 추가. 시트 template은 능력치 2행(정수 / 식) + AP + badstatus 5칸 + biography + items. 시트 클래스는 AsterActorSheet 공통(PARTS 분기) — 별도 클래스 불필요. 자동화 헬퍼(`applyDamageAndStatus`/`applyHealHealth`/`applyCureStatus`/`applyCureAllStatus`)는 Actor 일반 동작이라 *필드 추가만으로 NPC 자동화 즉시 가능*. `npcAction` Item·AP 자동 굴림·액션 시전·합체기 대상 여부는 후속(N2~N5). cr 라벨은 "도전 등급"(사용자 확정).

**배경:** D21에서 NPC 시트 미완성 명시. 자동화 헬퍼가 `actor.type` 분기 없이 `system.health`·`system.badstatus`만 참조함을 사전 검증 — NPC에 같은 필드 추가하면 헬퍼 변경 없이 동작.

**대안:**
- A. NPC 시트 클래스 분리: V13 PARTS로 type 분기 가능 — 별도 클래스는 actions/이벤트 중복
- B. 능력치 합산(PC와 동일): NPC는 식 기반(룰북 표) — 어긋남
- C. `formulas:{hit,dodge,ap}` 객체: 접근 경로 깊어짐 — 별도 필드가 input·헬퍼 접근 단순
- E. badstatus 일부만: PC와 불일치 시 헬퍼 분기 발생 — 5종 유지가 재활용 최대
- F. defendActive 필드: 이미 Combatant flag 기반 — DataModel 불필요
- G. ⭐ 별도 필드 + 공통 시트(PARTS) + 5종 badstatus + flag 유지: 본 결정

**실측 정합:**

- badstatus AE 동기화(`_preUpdate`/`_onUpdate` → `syncBadstatusEffect`)는 *type 가드 없음* — NPC도 졸림/피로 토글 시 상태 AE·아이콘 표시, 피로 AE의 `system.speed -3`도 NPC에 적용(NPC도 speed 필드 보유). 회귀 안전 + 일관 동작.
- i18n `ASTER.badstatus.*` 5종·`ASTER.label.health/speed`는 재사용, 신규는 `cr`/`ap`/`hitFormula` 등 라벨만.
- 시트 badstatus 체크박스 id는 `npc-` 접두사로 PC와 동시 열림 시 충돌 회피.

**선택 이유:** 자동화 헬퍼 재활용으로 D11 누적 효과 최대(헬퍼 코드 변경 0). 별도 필드는 객체 하위 키보다 input name·Roll 접근 단순. PARTS 분기로 시트 공통화. 5종 badstatus 일관(NPC 상태이상 면역은 *효과 영역*에서 처리, DataModel은 공통). Combatant flag 활용으로 방어·차지 상태는 DataModel 불필요. N1 우선 완성 후 N2~N5 점진(craft 트랙처럼 분할 안전).

> N 트랙 첫 STEP — 전투 시스템의 PC vs NPC 균형 회복 시작. **Actor 추상화 검증**: 헬퍼가 Actor 일반 동작 가능한 건 PC/NPC 공통 인터페이스(`system.health`·`system.badstatus`)가 잘 추상화된 결과 — N1만으로 PC 동등 자동화 즉시 가능. 향후 사역마 등 다른 Actor 타입도 같은 패턴.

## D48. N2 `npcAction` Item 타입 + 부분 구조화 + 시트

**결정:** NPC 스킬을 `npcAction` Item 타입으로 표현. DataModel은 *부분 구조화*(옵션 Y): `cost`/`costVariable`(가변 X) + `targetType`(self/one/many/all) + `damageFormula`/`addStatus`/`cureStatus`/`cureAllStatus`/`oncePerRound` + 자유 텍스트 `effect`/`description`. BaseItemModel 비상속(material·requirement 무의미). 별도 Item 시트(옵션 ㄴ)로 타 Item 타입과 일관. NPC 시트는 *액션 표 표시*(편집·삭제 버튼, 시전 버튼은 N3) + 일반 items 목록 분리. 공통 액션(대쉬·방어·집중)은 PC actions 패턴 재사용(N3, 하이브리드 옵션 다). 시전 흐름은 N2 영역 외.

**대안:**
- 옵션 X(자유 텍스트만): 자동화 어려움 — 큰 자동화 결정 어김
- 옵션 Z(완전 구조화): 자기 버프·적 약체까지 구조화 시 분량 큼, AE 자동화는 N2 외 — 부분 구조화가 균형
- BaseItemModel 상속: material·requirement 의미 없음 — 비상속이 명확
- 옵션 ㄱ(NPC 시트 inline 편집): 타 타입과 불일관 — 시드 검수·편집 표준 어김
- 옵션 가(모든 액션 npcAction): 공통 액션 중복 — 하이브리드가 최소 데이터

**선택 이유:**

(3) **타입 등록 인프라 일관** — template.json `types`+default + CONFIG.Item.dataModels + PARTS, 3곳 등록은 C2 craft 아이템과 같은 Foundry Item 확장 인프라.

(4) **자유 텍스트 보존(D30)** — `effect`/`description`은 자유 텍스트, 자기 버프·특수 효과는 자동화 외 GM 운영.

> N1(데이터 모델) + N2(스킬 아이템) 완료. 다음 N3(시전 흐름 + 공통 액션 + 헬퍼 호출). **Item 시스템 확장성**: craft 아이템(C2)·npcAction(N2)이 같은 인프라 재사용 — 향후 사역마·시나리오 자산도 같은 패턴.

## 부록: 결정의 커리어적 의미

이 일지는 단순 기록이 아니라 **설계 사고의 증거**다. 각 결정은 "특정 프레임워크 지식"이 아니라 "프레임워크가 바뀌어도 통하는 원칙"을 보여준다.

**원칙별 회수:**
- **데이터 정규화**: D1(참조 방식) — NoSQL embedding vs referencing
- **상태 vs 이벤트**: D3 → D14(차감/환불) — 룰 재해석으로 결정 갱신
- **플랫폼 기능 활용**: D4(아이템 타입), D16(Active Effect) — 자체 구현 대신 표준
- **점진 도입**: D6(인라인 문법), D13(마이그레이션) — "필요할 때 확장"
- **컴포넌트 반응형**: D10(컨테이너 쿼리)
- **관심사 분리·테스트 용이성**: D11(순수 함수) — D18(`computePenalties`)에서 두 번째 회수
- **definition-driven 설계**: D8(WORLD_VALUES) — D17(페이즈)에서 두 번째 회수, "비용 거의 0" 확장 검증
- **자동화의 경계**: D12 — D14(음수 허용 알림), D19(GM 버튼), D20(PL 즉시 회복)에서 일관 적용
- **공용 메커니즘 식별**: D19(장면 이동) — 세 룰(포만 감소·피크닉·부상)의 공통 트리거 추출

**결정을 *갱신한* 경험 (D3 → D14):**
초기 결정(자원 차감 안 함)을 일정 기간 운영한 뒤, 공식 표현 재독·사용자 멘탈 모델 부담을 근거로 정반대 정책(자동 차감 + 환불)으로 갱신. 옛 결정을 지우지 않고 supersession 표기로 보존해 *왜 그때 그랬고 왜 지금 바꾸는지*의 흐름이 그대로 남도록 했다. 결정 일지의 가치는 정확함이 아니라 사고 과정의 흔적이다.

**룰 재독으로 명세를 정정한 사례 (D18):**
초기 명세에서 보정 적용 범위를 페이즈에 묶어 추측했으나, 룰 재확인으로 보정과 감소가 별도 영역임을 확인하고 명세를 정정. 추측-검증-정정의 사이클을 명세 단계에서 닫은 사례.

**면접 활용:**
"이 프로젝트에서 가장 고민한 설계 결정"에 D1·D3↔D14·D11·D19 중 하나를 *대안과 갱신 흐름까지* 설명하면 강한 답이 된다. 특히 D3→D14는 "결정을 다시 평가하는 능력"을 직접 보여주는 사례.
